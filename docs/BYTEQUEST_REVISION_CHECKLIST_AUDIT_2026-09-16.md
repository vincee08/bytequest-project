## Specification and repository discovery

- The path named in the request, `docs/new-bytequest-revisions-to-do-list.pdf`, is absent. The mandatory reference path, `docs/reference/new-bytequest-revisions-to-do-list.pdf`, exists and is the document audited here.
- The PDF was extracted before application changes with the temporary `pdf-parse` CLI because `pdftotext` and other installed PDF readers were unavailable. The extracted specification contains BQ-001 through BQ-032.
- The repository contains a Flutter/Dart learner application (`ByteQuest-Mobile-App`), a Next.js/React/TypeScript Instructor and Administrator dashboard (`ByteQuest-Web-Dashboard`), Supabase Auth/PostgreSQL/Storage/Realtime migrations (`supabase`), lifecycle and security verification scripts (`scripts`), and architecture/audit material (`docs`).
- Supabase/PostgreSQL is the authoritative assessment and authorization layer. Flutter records evidence and consumes released results; Instructor finalization/release is server-authorized.
- Official local references are present under `docs/reference/tesda_sources/`: the amended Computer Systems Servicing NC II Training Regulations, TESDA Circular No. 18 s. 2015, and current/per-COC Self-Assessment Guides. Repository traceability documents explicitly separate official TESDA requirements from ByteQuest operational scoring and gamification.

## Status definitions

- **IMPLEMENTED** — code, schema, and/or tests provide direct evidence that the acceptance condition exists.
- **PARTIALLY IMPLEMENTED** — useful implementation exists, but a stated acceptance condition or its verification is incomplete.
- **NOT IMPLEMENTED** — no material implementation was found.
- **BLOCKED** — completion depends on missing authoritative information or an unavailable external/runtime prerequisite.

## Dependencies and blockers identified before implementation

1. **Hosted deployment:** the local schema includes three newer migrations (`20260915090000`, `20260916090000`, and `20260916100000`) that have been reset and tested locally but not applied to the hosted Supabase project. No production migration will be applied without explicit deployment authorization.
2. **Android execution:** Flutter dependency resolution, analysis, and widget/unit tests are available, but `flutter build apk --debug` and device launch are blocked because the Android SDK/toolchain and an Android target are not installed/available.
3. **Manual visual regression:** automated responsive/widget coverage exists, but a final human screenshot review on representative Android devices remains outstanding.
4. **External AI runtime:** live OpenRouter behavior depends on a valid server-only key, model availability, rate limits, and provider uptime. Provider errors are handled, but those external conditions cannot be guaranteed by source code.
5. **TESDA policy boundary:** the supplied official sources contain competency units/evidence requirements but do not establish a universal numeric passing score, assessment-component weights, XP, or star policy. Those values must not be invented.

## Minimal implementation plan

- Change only BQ-015: reduce completed interaction-control clutter in the reusable Flutter interaction components while preserving state, feedback, accessibility, and an explicit review/change path.
- Add focused widget regression coverage for the completed/collapsed state and correction path.
- Do not alter TESDA content, scoring policy, role architecture, database schema, LMS flows, AI workflow, or already-correct mission definitions.
- Re-run focused Flutter tests, the full Flutter test/analyzer suite, dashboard checks, and available Supabase checks; record unavailable gates honestly.
