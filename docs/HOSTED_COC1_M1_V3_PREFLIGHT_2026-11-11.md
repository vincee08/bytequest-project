## 2. Backup and recovery readiness

**No recoverable hosted backup is verified.** Backup-list access returned 403; no restore test or backup coverage inspection was possible. Supabase states that managed daily backups depend on plan, PITR has its own restore window, and database backups include Storage metadata but **not Storage object bytes**. A daily restore can entail downtime; restoring an earlier point replaces later database changes. Its [backup guide](https://supabase.com/docs/guides/platform/backups) recommends restoring to a new project to preserve the current project.

Before any approved production change, the owner should:

1. Record a completed backup or PITR point taken immediately before the maintenance window, the retention deadline, and the earliest/latest recoverable times. If managed backups are unavailable, arrange an encrypted, access-controlled logical export with roles, schema, data, and migration history. Include `auth`, application tables, `storage` metadata, and hosted-only `td_*` objects; separately preserve actual Storage object bytes and environment/configuration inventory. The [Supabase CLI backup/restore guide](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore) documents role/schema/data exports and special handling for migration history and managed-schema customizations. Do not put exports in the repository or unsecured QA storage.
2. Restore a backup to a **separate secured project or isolated target**, never over production for the test. Confirm auth/profile counts, 297-or-current COC1 M1 actions, practice completions, assessment attempts/scores/releases, `td_*` objects, RLS, functions, and sample Storage object access. A backup listing alone is not proof of recovery.
3. Record a cutover time and a recovery point objective. For a failed forward migration, prefer a reviewed forward correction that leaves appended evidence intact. A whole-project restore would discard post-backup writes and require downtime; use only if the owner accepts that data-loss window. No inverse SQL that rewrites or deletes learner evidence is proposed.
